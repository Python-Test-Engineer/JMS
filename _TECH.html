JMS — Technical Specification

What this is. The implementation contract for JMS v1. It turns _PLAN.md into a browser application: a TypeScript Node service, HTMX-rendered templates, a SQLite database with typed repositories, server-side authorisation, PDF job sheets/invoices, a reproducible seed dataset and verified, scheduled backups.

Status. Draft v0.2.0 — ready to build. _PLAN.md remains the product authority; this document is the engineering authority. Where the two differ, §1.3 records the change explicitly.

Documentation rule. _PLAN.md, _TECH.md and help pages are HTML-only. Markdown is converted to HTML or authored directly. The application itself does generate PDF job sheets and invoices.

1. Scope, decisions and conventions

1.1 What v1 builds

A single deployable TypeScript web application for Acme Windows that provides:

  • sign-in, first-sign-in password change, sessions and server-side authorisation;
  • an editable role × action permission matrix;
  • customers, customer portal logins, jobs, assignments, scheduling and status tracking;
  • a customer portal limited to the customer's own jobs, updates and documents;
  • invoices with gapless numbering and server-generated PDFs;
  • global search, operations/engineer dashboards, timeline, workload and financial views;
  • an admin area for users, roles, permissions, company settings, themes and audit;
  • a SQLite database accessed only through typed repositories, with forward-only migrations, integrity checks and online backups;
  • a cron-driven backup routine that produces verified snapshots, enforces retention and can be restored by one documented command.

1.4 Data and code conventions

  • IDs: UUID v4 strings generated with crypto.randomUUID(), branded at the type level (§1.5). SQL columns are TEXT PRIMARY KEY.
  • Timestamps: UTC ISO 8601 strings (2026-03-16T08:00:00.000Z). Render in the company timezone. Never store local-time strings. ISO strings sort chronologically.
  • Dates: business dates use YYYY-MM-DD only where a time is meaningless; invoice due dates are stored as instants and displayed locally.
  • Money: integer minor units (price_net: 425000 means £4,250.00).
  • VAT: integer basis points (vat_rate_bp: 2000 means 20.00%).
  • Percentages: basis points unless stated otherwise.
  • Quantities: integer thousandths (qty_milli: 1500 means 1.500).
  • Emails: lower-cased and trimmed before uniqueness checks; the database also uses COLLATE NOCASE for the unique indexes.
  • Soft deletion: jobs and customers use archived_at; invoices use VOID; audit, events and migrations are append-only and never deleted.
  • Validation: reject unknown fields on writes; coerce only form strings explicitly.
  • Escaping: Nunjucks autoescape on. Notes are plain text, never HTML.
  • No secrets in code: configuration comes from environment variables.
  • No any: unknown at boundaries, Zod to narrow, assertNever for exhaustiveness.
  • No floating promises: every promise is awaited, returned or explicitly voided with a comment; ESLint enforces this.

1.5 Robustness rules (non-negotiable)

These apply to every module, including scripts and tests.

  1. Parse, do not cast. Data from HTTP, environment, SQLite, settings JSON and files is unknown and must pass a Zod schema before it is used. as is permitted only in brand constructors and migration adapters, each with a comment.
  2. Branded identifiers. UserId, CustomerId, JobId, InvoiceId and CompanyId are branded strings. Mixing them is a compile error. Constructors validate UUID shape.
  3. Typed errors. Expected failures return a discriminated Result<T, DomainError>; unexpected failures throw AppError subclasses with a stable code and HTTP status. Routes never format error text; the central handler does.
  4. Exhaustive unions. Status, role and event enums are unions derived from as const arrays; every switch ends in assertNever(value). The status transition table is satisfies Record<JobStatus, ...>, so a new status cannot be forgotten.
  5. One writer path. All mutations go through a service and a repository inside a SQLite transaction. Controllers never issue queries; repositories never render.
  6. Optimistic concurrency. Mutable records carry version INTEGER NOT NULL DEFAULT 1. Updates use WHERE id = ? AND version = ?; a zero-row update returns 409 CONFLICT, never a silent overwrite.
  7. Idempotent mutations. Every unsafe form carries a hidden _idempotency token. idempotency_keys records (key, user_id, route) inside the mutation transaction; a replay returns the recorded outcome instead of creating a second record.
  8. Transactions are short. No PDF rendering, filesystem sync, network call or logging I/O happens inside a transaction. Long work is staged outside, then committed.
  9. Fail closed. Missing permissions, missing records, malformed sessions and unknown scopes return the safe response. Startup refuses to serve on failed migration checks, failed integrity checks or a missing production secret.
  10. Atomic files. Generated files are written to a temp name in the same directory, fsynced, renamed, then checksum-verified. Partial files are never served.
  11. Tests prove the invariant. Every rule in §16.6 and every backup rule in §17.11 has an automated test that fails if the rule is removed.
  12. Boring dependencies. No runtime dependency without a maintained release, TypeScript types and a documented purpose in §3.1.

2.1 Runtime shape

Browser (HTMX + progressive forms)
        │  HTTP, cookies, HTML fragments
        ▼
Express 5 app (TypeScript, compiled to dist/)
  ├─ middleware: request id, logging, security headers, sessions, CSRF, auth, permissions
  ├─ routes/controllers: parse (Zod), authorise, call services, render typed view models

  ├─ repositories: typed Kysely queries, row decoding, optimistic concurrency
  └─ templates: Nunjucks layouts, pages, partials, macros
        │
        ├─ data/jms.sqlite       domain + sessions + audit (one WAL database)
        ├─ storage/documents/    generated PDFs (regenerable, not authoritative)
        └─ backups/              verified snapshots, manifests, checksums

2.2 Layers and the dependency rule

Dependencies point inward only:

routes ──▶ services ──▶ repositories ──▶ db (Kysely)
   │           │             │
   └──▶ views  └──▶ domain   └──▶ contracts (Zod schemas + inferred types)
  • src/domain/ is pure: no Express, no SQL, no filesystem, no clock reads (time is passed in). It is unit-testable in isolation.
  • src/contracts/ holds Zod schemas and the types inferred from them. These are the only shared shapes between HTTP, services and persistence.
  • src/repositories/ owns SQL. It decodes rows with Zod into domain records and returns branded IDs. It never returns Kysely row types to callers.
  • src/services/ owns transactions and business rules. It returns Result values for expected failures and throws AppError only for infrastructure failures.
  • src/routes/ is thin: parse, guard, call, render/redirect.
  • src/views/ receives view models typed in src/views/view-models.ts; templates do not call services and do not query.

The dependency rule is enforced in CI by an import-boundary lint rule (eslint-plugin-import-x with zone rules): routes may import services/contracts/domain; services may not import routes or views; domain may import nothing but contracts and utility modules; repositories may not import services.

2.3 Request lifecycle

  1. Express assigns a request ID (or validates an incoming X-Request-Id) and starts a Pino child logger.
  2. Security headers are set; static files are served with immutable cache headers.
  3. The session cookie is read, its HMAC verified and its SHA-256 looked up. Idle and absolute expiry are checked in one query.
  4. The authenticated user is loaded; deactivated/archived users have all sessions revoked and are signed out.
  5. CSRF is verified for every unsafe method (POST, PUT, PATCH, DELETE) with a constant-time comparison.
  6. The route guard runs requirePermission(actionKey).
  7. The controller parses the body/query with a Zod schema, rejecting unknown keys.
  8. The controller calls a service, which applies object scoping, domain rules and optimistic concurrency.
  9. The service writes domain changes, events and audit rows inside one transaction.
  10. The controller renders a full page or an HTMX fragment and sets flash data.
  11. The response is sent only after the transaction has committed. A failed commit is a 500 with the request ID; no in-memory state is left ahead of disk.

2.4 Process model and concurrency

  • One application process. SQLite WAL allows safe concurrent backups and read-only inspection, but the in-process rate limiter, session throttling and single-writer assumptions make multiple app replicas unsupported in v1.
  • A startup lock (data/jms.lock, PID + boot time) prevents an accidental second instance. Stale locks are removed only after checking the PID is dead or belongs to a different boot.
  • SQLite is configured with busy_timeout; write transactions use BEGIN IMMEDIATE and a bounded retry for SQLITE_BUSY/SQLITE_LOCKED (§7.4).
  • Cron backups run in a separate process against the same file using SQLite's online backup API. They do not stop the app and do not produce torn copies.
  • restore, migrate and seed --force take an exclusive advisory lock (flock on data/jms.ops.lock) and refuse to run while the app is serving, unless --offline is explicitly confirmed.

5.3 Directories and boot checks

On boot the app:

  1. ensures data/, backups/ and storage/documents/ exist and are writable;
  2. opens SQLite read-write and applies pragmas (§7.1);
  3. verifies the migration checksum table and refuses to start on a mismatch;
  4. runs PRAGMA quick_check and PRAGMA foreign_key_check; failures are fatal and name the latest verified backup;
  5. acquires the application lock and writes its PID;
  6. starts the HTTP listener only after all checks pass.

6.2 HTMX rules

  • The client sends HX-Request: true; the server exposes a typed req.isHtmx boolean.
  • HTMX responses return a fragment, never a full document.
  • Full-page forms are the baseline. Every create/edit form works without JavaScript.
  • Lists, search, filters, status control and timeline refresh use HTMX.
  • After a mutation, return the updated fragment and trigger a flash event.
  • Set HX-Redirect only when a full navigation is genuinely needed.
  • Disable submit buttons on submit (app.js); show an inline busy state within 300 ms.
  • Never rely on client-side checks for authorisation or validation.

6.3 CSRF and flash

  • A 32-byte random CSRF token is created per session and stored with the session row.
  • Full forms include <input type="hidden" name="_csrf" value="…">.
  • HTMX requests send X-CSRF-Token from a <meta> tag.
  • Comparison uses crypto.timingSafeEqual on equal-length buffers.
  • Missing/invalid token → 403, no state change.
  • Flash messages are stored in the session as { type, message } and rendered once.

6.4 Errors and not-found behaviour

  • Signed-in users never see a raw stack trace.
  • Out-of-scope records return the friendly not-found page, not a 403, to avoid ID probing.
  • A friendly 403 explains the missing permission and links to the user's landing screen.
  • Validation errors re-render the form with values preserved and focus on the first error.
  • Every error response carries X-Request-Id; the same ID appears in the log line.

6.5 Pagination, filtering and sorting

  • Default page size 25; maximum 100.
  • ?page=2&per_page=25; invalid values fall back to defaults (Zod coercion, bounded).
  • Sort/filter parameters are allow-listed per list; unknown keys are rejected with 400.
  • Search requires at least 2 characters.
  • Lists show a count and the active filters as removable pills.
  • All list queries are parameterised and capped by LIMIT/OFFSET; no unbounded scans.

7. SQLite database

7.1 File and pragmas

One database file holds domain data, sessions, rate limits, idempotency keys and audit. The database is authoritative; generated PDFs are regenerable and are not part of the consistency boundary.

src/db/connection.ts opens better-sqlite3 and applies, in order:

PRAGMA journal_mode = WAL;          -- readers never block the writer
PRAGMA synchronous = FULL;          -- production; NORMAL allowed in dev only
PRAGMA foreign_keys = ON;           -- every FK enforced
PRAGMA busy_timeout = 5000;         -- wait, then fail with a typed error
PRAGMA trusted_schema = OFF;        -- no schema-embedded code
PRAGMA temp_store = MEMORY;         -- no temp files in the data directory
PRAGMA wal_autocheckpoint = 1000;   -- bound WAL growth
PRAGMA optimize;                    -- after migrations and on graceful shutdown

journal_mode, synchronous and foreign_keys are asserted at boot; a database that cannot honour them refuses to open. better-sqlite3 runs statements synchronously, so a query cannot be interleaved with a half-applied transaction in the same process.

7.2 Schema conventions

  • Every table has an explicit PRIMARY KEY; join tables use a composite primary key.
  • Every foreign key declares ON DELETE RESTRICT (default) or ON UPDATE CASCADE only where documented. Nothing is ON DELETE CASCADE except invoice_lines, which belongs to its invoice and is deleted with it inside a transaction.
  • Enumerations are TEXT with CHECK (column IN (...)), generated from the same constant arrays used by TypeScript.
  • Every timestamp is TEXT NOT NULL ISO 8601 UTC; nullable timestamps are explicitly nullable. CHECK guards format where practical.
  • Money is INTEGER with CHECK (value >= 0); quantities are INTEGER thousandths.
  • Booleans are INTEGER NOT NULL CHECK (value IN (0,1)).
  • Uniqueness that is case-insensitive uses COLLATE NOCASE or a unique index on lower(column).
  • Mutable tables carry version INTEGER NOT NULL DEFAULT 1; updates increment it.
  • Partial unique indexes express "at most one active" rules (lead assignment, live invoice).

  • Repository methods take and return domain types and branded IDs, never unknown rows.

7.4 Transactions, retries and isolation

src/db/transaction.ts exposes one write helper:

export function writeTx<T>(db: Database, fn: (tx: Kysely<DB>) => T): T {
  const run = db.transaction(() => fn(tx));
  return withBusyRetry(() => run.immediate(), { attempts: 5, baseDelayMs: 20 });
}
  • Writes use BEGIN IMMEDIATE, acquiring the write lock before reading mutable state.
  • Nested calls use SAVEPOINT/RELEASE via better-sqlite3's transaction nesting; a service may compose repository calls inside one outer transaction.
  • withBusyRetry retries only SQLITE_BUSY and SQLITE_LOCKED, with exponential backoff plus jitter, and gives up with AppError("DB_BUSY", 503).
  • Transactions never exceed 100 ms of work in the v1 dataset. Anything slower is staged outside the transaction and committed in a short second step.
  • Reads use the Kysely handle directly; WAL gives them a consistent snapshot.

7.5 Migrations

Migrations are numbered SQL files applied in order:

src/db/migrations/0001_init.sql
src/db/migrations/0002_indexes.sql

The runner:

  1. takes the ops lock (§17.3) and writes a pre-migration backup;
  2. creates schema_migrations(version INTEGER PRIMARY KEY, name TEXT NOT NULL, checksum TEXT NOT NULL, applied_at TEXT NOT NULL);
  3. verifies every applied file's SHA-256 matches the recorded checksum — mismatch is fatal;
  4. applies pending files each inside one transaction, recording version, name, checksum and timestamp, then sets PRAGMA user_version;
  5. runs PRAGMA foreign_key_check, PRAGMA quick_check and PRAGMA optimize;
  6. refuses to run if the app holds the live lock, unless --offline is passed.

Rules:

  • Applied migrations are immutable. Fixes are new migrations.
  • Migrations are forward-only. A down migration is not shipped; restoring a verified backup is the rollback path.
  • seed --force and reset also require the ops lock and write a backup first.
  • Boot compares user_version with the highest packaged migration and exits with a clear "run npm run db:migrate" message when they differ.

9. Authentication and sessions

9.1 Sign-in

POST /signin accepts email, password, _csrf, optional next.

  1. Normalise email; rate-limit by IP + email using the SQLite-backed limiter.
  2. Find an active user. A missing user and a wrong password produce the same generic error and comparable timing (verify against a dummy Argon2id hash when the user is missing).
  3. Verify with Argon2id. On failure: audit auth.signin.failed, increment the limiter, re-render the form with a plain-language message.
  4. On success: create a new session row, set the signed cookie, clear old sessions for the same browser only if one is presented, update last_login_at, audit auth.signin.success, clear the email limiter key.
  5. If must_change_password, redirect to /account/password and allow only password change, sign-out and static assets until it is cleared.
  6. Otherwise redirect to next if it is a safe same-origin path, else to the role landing page: ADMIN/MANAGER → /dashboard/operations; ENGINEER → /my-jobs; CUSTOMER → /portal/jobs.

9.2 Session lifecycle

  • Cookie name: jms_sid in development; __Host-jms_sid in production.
  • Value: 32 random bytes, base64url, signed with HMAC-SHA-256 using SESSION_SECRET.
  • The database stores only SHA-256 of the raw token. The raw token is never logged or persisted.
  • Attributes: HttpOnly, SameSite=Lax, Path=/, Secure in production.
  • Idle expiry 60 minutes (configurable). expires_at slides on activity; persistence is throttled to once per minute per session.
  • Absolute expiry 12 hours from sign-in, checked independently of the idle window.
  • Sign-out marks the row revoked_at and clears the cookie.
  • Password change, role change, deactivation, archive or a support "revoke sessions" action revokes all sessions for the user inside the same transaction.
  • A revoked or expired cookie redirects to sign-in with an explanation; the original form state is not promised.
  • On boot, expired sessions are deleted and rows for non-active users are revoked.

9.3 Password rules

  • Hash with Argon2id: memory 19 MiB, iterations 2, parallelism 1, 16-byte salt, 32-byte output. Parameters are constants in auth/passwords.ts and recorded in the PHC string so they can be raised later without breaking existing hashes.
  • Rehash on successful sign-in when the stored parameters are below the current policy.
  • Minimum 10 characters, at least one letter and one digit; maximum 200 characters.
  • Reject the user's email, display name and JMS123 as a new password.
  • DEFAULT_PASSWORD is only for invites/seed and always sets must_change_password.
  • Password change requires the current password (unless the account is in forced-change mode, where the session already proves the default password).
  • Password hashes are never logged, rendered or audited.

9.4 First sign-in / change password

  • /account/password is available to every authenticated user.
  • Forced-change mode is a middleware gate: any other page redirects there.
  • Success clears must_change_password, revokes all other sessions, keeps the current session (with a rotated token and row), audits auth.password.change.
  • Rotation is one transaction: insert the new session, revoke the old, update the user. The response sets the new cookie only after commit.

9.5 Rate limiting

SQLite-backed fixed windows survive restarts and do not grow without bound:

Scope Limit Window Action
Sign-in by IP + email 5 failures 15 min block 15 min
Sign-in by IP 20 failures 15 min block 15 min
Password reset by user 3 60 min block
Search 60 requests 1 min 429 with retry hint

Keys are HMACs of the scope plus the IP/email so raw addresses are not stored in a table that outlives the window. Expired rows are pruned on write and by nightly maintenance. Successful sign-in clears the email key. Limiter checks happen before password verification and before any database write that could leak timing.

9.6 Password reset and invites

  • Staff with user.reset.password can issue a new temporary password. It is displayed once, stored hashed, and sets must_change_password.
  • customer.invite creates or repairs a CUSTOMER login for a customer record: default password, INVITED, must_change_password, audit.
  • No email delivery in v1; the screen states the temporary password and asks staff to pass it on securely.
  • Issuing a reset revokes every session for that user before the new hash is stored.

10.3 Object-level scoping

These are code invariants, not permission cells.

Customer scope

  • A CUSTOMER user has exactly one customer_id.
  • Every job query adds job.customer_id = :customerId.
  • Direct access to another customer's job, invoice or document returns 404.
  • Customer responses use a customer presenter that removes price_net, price_gross, internal_notes, internal events, other customers and engineer phone numbers.

Engineer scope

  • An ENGINEER sees jobs with an active assignment (removed_at IS NULL) plus jobs they completed in the last 90 days.
  • Direct access to another engineer's job returns 404.
  • Engineer responses remove price, invoice and internal-note fields.
  • A field-capable MANAGER assigned to a job gets the same field affordances, but their role also grants broader visibility.

Manager/Admin scope

  • See all jobs, customers, invoices and insights.
  • Admin-only areas remain gated by the admin action keys.

Customer records for engineers

  • customer.view.own for an ENGINEER means the customer record of a job they are assigned to, including phone (needed on site), but not other customers and not exports.

src/domain/scoping.ts builds a JobScope union (AllScope, AssignedScope, CustomerScope) and the repository turns it into a parameterised WHERE clause. A route cannot pass a raw user ID into SQL; it passes a scope object.

10.4 UI visibility is not enforcement

  • res.locals.can is a function bound to the current user.
  • Nav pills and buttons render only when can is true.
  • Every route and every HTMX partial repeats the check server-side.
  • Hidden fields never carry role, owner or permission decisions.
  • A permission change applies on the next request because the matrix is read from the store and the user is reloaded per request.

10.5 Safeguards the matrix cannot remove

  1. At least one ACTIVE ADMIN must exist at all times.
  2. The last Admin cannot remove their own admin.permissions.edit, deactivate themselves or change their own role.
  3. admin.audit.view cannot be granted to CUSTOMER or ENGINEER; the save endpoint rejects it with a validation error and an explanation.
  4. Every matrix edit writes an audit row with role, action key, before and after.
  5. System roles cannot be deleted or renamed in v1.

These are enforced in services/permissions.ts inside a transaction, not only in the UI. The last-admin check uses SELECT count(*) … WHERE role_key = 'ADMIN' AND status = 'ACTIVE' with the write lock held.

11.2 Transition algorithm

src/domain/status.ts exports a fully typed table and guard:

export const TRANSITIONS = {
  DRAFT:       { allowed: ["SCHEDULED", "CANCELLED"], /* … */ },
  SCHEDULED:   { allowed: ["IN_PROGRESS", "ON_HOLD", "CANCELLED", "SCHEDULED"], /* … */ },
  IN_PROGRESS: { allowed: ["COMPLETED", "ON_HOLD"], /* … */ },
  ON_HOLD:     { allowed: ["IN_PROGRESS", "CANCELLED"], /* … */ },
  COMPLETED:   { allowed: ["INVOICED", "IN_PROGRESS"], /* … */ },
  INVOICED:    { allowed: ["PAID", "COMPLETED"], /* … */ },
  PAID:        { allowed: [], /* … */ },
  CANCELLED:   { allowed: [], /* … */ },
} as const satisfies Record<JobStatus, TransitionRule>;

export function canTransition(input: TransitionInput): Result<TransitionPlan, DomainError>;

Checks in order:

  1. to is in the transition table for job.status.
  2. The user has job.status.override, or is an assigned field-capable user taking one of the forward field transitions (SCHEDULED → IN_PROGRESS, IN_PROGRESS → COMPLETED, IN_PROGRESS → ON_HOLD, ON_HOLD → IN_PROGRESS).
  3. DRAFT exit guards are met.
  4. Required note/reason is present where the transition demands it.
  5. The target is not invoice-controlled (INVOICED, PAID) for the generic route.

On success, in one transaction: update the job with version check, stamp actual timestamps, append JobEvent, append audit row. Return the updated job. A failed version check returns 409 and changes nothing.

11.3 Assignments

  • Only field-capable active users may be assigned.
  • The assign screen shows active ENGINEERs and field-capable MANAGERs.
  • Saving replaces the active assignment set: new rows inserted, removed rows get removed_at (never deleted), lead changes recorded.
  • At most one active lead. If the lead is removed, the manager must choose a new lead or the save is rejected with a clear message.
  • Assignment changes append ASSIGNMENT events and audit rows. A newly assigned field user sees the job immediately under My jobs.
  • Removing an engineer from a SCHEDULED job is allowed but shows a warning if it would leave no active assignee while dates are set.
  • The whole save is one transaction; the partial unique indexes are the final backstop.

11.4 Scheduling and conflicts

POST /jobs/:id/schedule accepts planned_start, planned_end, planned_slot.

  • Validate start/end and timezone conversion with Luxon; reject Invalid DateTime.
  • Find overlapping active assignments for each selected field user where the other job is SCHEDULED, IN_PROGRESS or ON_HOLD and its planned range overlaps. The overlap query is other.planned_start < :end AND other.planned_end > :start and is indexed.
  • Conflicts are advisory: return a warning naming the engineer and the clashing job. The form offers Save anyway; the save records a SCHEDULE_CHANGE event mentioning the accepted conflict.
  • Rescheduling a SCHEDULED job keeps the status SCHEDULED and writes an event; it does not use the status endpoint.
  • Leaving DRAFT is offered once dates and an assignee exist; the UI defaults to yes.

11.5 References and numbering

  • Job reference: JOB-${year}-${String(seq).padStart(4, "0")}, year from the company-local creation date.
  • Invoice number: INV-${year}-${String(seq).padStart(4, "0")}.
  • sequences(kind, year) is updated with UPDATE … RETURNING value inside the creating transaction (BEGIN IMMEDIATE), so two creates cannot read the same number.
  • Invoice numbers are gapless: voiding keeps the number, re-issuing takes the next one.
  • References are immutable after creation.
  • Duplicate references are impossible because allocation and insert share one transaction and the unique index is the backstop.

11.6 Notes and visibility

  • internal_notes is a single internal field on the job, visible to staff and assigned engineers, never to customers.
  • customer_notes is customer-visible.
  • Timeline notes choose INTERNAL or CUSTOMER visibility; the UI labels the choice plainly and never defaults to customer-visible.
  • A note is plain text; line breaks are preserved, HTML is escaped.
  • Pricing notes must not be placed in internal_notes if engineers should not see them; use the internal timeline with a manager-only audience. In v1, engineers see internal notes; customers never do.

11.7 Invoices

  • Create from a COMPLETED job or from the invoice list with a job selector.
  • Default lines from the job title and price_net; manager can edit lines.
  • Save as DRAFT, then preview the PDF, then Issue.
  • Issue: allocate number if not already allocated, set issued_at, due_at from company terms, set invoice ISSUED, set job INVOICED, write events/audit.
  • Mark paid: ISSUED → PAID, stamp paid_at, set job PAID, event/audit.
  • Void: ISSUED → VOID, stamp reason, set job back to COMPLETED, keep number and record.
  • Re-issue after void creates a new DRAFT with the next number.
  • Financial views use invoice net for invoiced and paid amounts.
  • All monetary totals are recomputed from invoice_lines in the transaction; a mismatch with the submitted total is a validation error, not a silent correction.

11.8 Documents and PDFs

  • Job sheet and invoice PDFs are generated on demand by services/documents.ts.
  • Every generation appends a documents row with version, checksum, size and path.
  • The file path is derived from the document ID, never from user input.
  • A missing file is regenerated; a stale file is never served by a cached URL.
  • Access rules are evaluated before generation, not after.
  • Generation is staged: render to a temp file, fsync, rename to storage/documents/{id}.pdf, compute SHA-256, then insert the document row. If the insert fails, the file is deleted and the error is returned.

11.9 Archive and audit

  • Archive job/customer sets archived_at; it disappears from normal lists but remains searchable by admins in the archive view.
  • Restore clears archived_at.
  • Delete is not exposed for jobs, customers or invoices.
  • Every state change in §16.3 writes an audit row in the same transaction.
  • Archived records remain visible to the customer portal only if the plan says so; v1 hides archived jobs from customers but keeps invoice history.

12.10 Controller pattern

router.post(
  "/jobs/:id/status",
  requirePermission("job.status.advance"),
  idempotent(),
  asyncHandler(async (req, res) => {
    const user = requireUser(req);
    const job = await jobs.getVisibleOr404(user, JobId.parse(req.params.id));
    const result = await jobs.transition({
      user,
      job,
      to: StatusBody.parse(req.body),
      meta: writeMeta(req),
    });

    if (!result.ok) return res.status(statusFor(result.error)).render(
      "pages/jobs/detail.njk",
      jobDetailView({ user, job, errors: [result.error] }),
    );

    if (req.isHtmx) return res.render("partials/jobs/status.njk", statusView(result.value));
    setFlash(req, "success", "Job status updated.");
    return res.redirect(`/jobs/${job.id}`);
  }),
);

  • Backups contain personal data and password hashes. The backups/ directory is mode 0700, files 0600, owned by the service account.

Automated tests must cover:

17. Backups, restore and cron

Backup is a product feature, not an afterthought. The database is one file; the loss of that file is the loss of the business record. The following rules are mandatory.

17.1 Objectives

Measure Target
RPO (maximum data loss) 24 hours with nightly cron; 15 minutes if the optional hourly job is enabled
RTO (time to restore) under 30 minutes for the v1 dataset
Backup retention 30 daily, 12 weekly, 12 monthly (GFS)
Verification every backup is integrity-checked; latest is restore-tested nightly
Offsite encrypted copy after every successful local backup
Monitoring /healthz and an external dead-man's switch

17.2 Backup format and naming

backups/
  jms-20260316T021500Z-nightly.db
  jms-20260316T021500Z-nightly.db.sha256
  jms-20260316T021500Z-nightly.json
  jms-20260317T021500Z-nightly.db
  ...
  • Timestamp is UTC, sortable (YYYYMMDDTHHmmssZ).
  • tag is nightly, hourly, manual, pre-migrate, pre-seed or pre-restore.
  • .db is a complete, consistent SQLite snapshot (online backup API), not a zip and not a -wal sidecar.
  • .sha256 contains the hex digest and filename in sha256sum format.
  • .json is a manifest validated by a Zod schema:
{
  "schema": 1,
  "file": "jms-20260316T021500Z-nightly.db",
  "tag": "nightly",
  "created_at": "2026-03-16T02:15:00.000Z",
  "sqlite_version": "3.49.1",
  "user_version": 2,
  "size_bytes": 912345,
  "sha256": "…",
  "integrity": "ok",
  "foreign_key_check": "ok",
  "counts": { "users": 22, "customers": 10, "jobs": 26, "invoices": 6 },
  "duration_ms": 84,
  "host": "jms-prod-1"
}

The manifest is written last, after the checksum and verification pass. A .db without a manifest is treated as unverified and is not eligible for pruning or restore-by-latest.

17.3 Online snapshot procedure

src/backup/snapshot.ts runs in the CLI process:

  1. Acquire the ops lock with flock -n semantics; if another backup/migration/restore holds it, exit 0 with "skipped: lock held" (for cron) or 3 for manual runs.
  2. Check free space in BACKUP_DIR; refuse below BACKUP_MIN_FREE_MB.
  3. Open the live database read-only and run PRAGMA quick_check first; a failing live database aborts the backup and raises a critical log line.
  4. Use SQLite's online backup API (better-sqlite3 db.backup(destination)) to write backups/.tmp-<name>.db. The API copies pages consistently while writers continue.
  5. fsync the temp file and its directory, then rename to the final name.
  6. Open the snapshot read-only and run: - PRAGMA integrity_check (must return ok); - PRAGMA foreign_key_check (must return no rows); - a count of core tables for the manifest.
  7. Compute SHA-256 and write .sha256.
  8. Write the manifest atomically (temp + rename), then log one JSON line with name, size, duration and counts.
  9. If BACKUP_OFFSITE_CMD is set, run it with the snapshot path as a fixed argument; a non-zero exit marks the backup offsite_failed in a sidecar status file but does not delete the local copy.
  10. Release the lock.

Failure at any step leaves the previous verified backups untouched and deletes the temp file. The command exits non-zero so cron/monitoring can alert.

17.4 Verification

jms verify --latest and jms verify --file <name>:

  1. Verify the .sha256 matches the file.
  2. Parse and validate the manifest.
  3. Run PRAGMA integrity_check and PRAGMA foreign_key_check on a copy (never the only copy).
  4. Open the snapshot in a temp directory, apply no migrations, and run a read-only smoke query: company exists, an admin exists, counts are non-zero, user_version matches the manifest.
  5. For --full, run the test suite's restore smoke test against the temp copy.
  6. Print a single summary and exit 0/1.

The nightly cron runs verify --latest after the backup. A weekly drill restores the latest snapshot into a throwaway directory and starts the app on a spare port with NODE_ENV=test, then fetches /healthz and /signin.

17.5 Schedule and cron

The recommended deployment uses system cron, not an in-process timer. Cron survives an application crash, runs even when the app is down, and keeps backup code out of the request process. If a host has no cron, the systemd timer in ops/systemd/ is equivalent. An in-process scheduler is not provided in v1.

ops/cron/jms-backup (install as /etc/cron.d/jms-backup, owned by root, mode 0644):

# JMS verified database backups. Times are server-local; log lines are UTC.
SHELL=/bin/sh
PATH=/usr/local/bin:/usr/bin:/bin
TZ=UTC

# Nightly snapshot + verification at 02:15.
15 2 * * * jms cd /srv/jms && /usr/bin/flock -n /srv/jms/data/jms.ops.lock \
  /usr/bin/node dist/cli/jms.js backup --tag nightly >> /var/log/jms/backup.log 2>&1

# Verify the newest snapshot at 03:15 (after the backup finishes).
15 3 * * * jms cd /srv/jms && /usr/bin/node dist/cli/jms.js verify --latest \
  >> /var/log/jms/backup.log 2>&1

# Prune by GFS at 03:45, but never remove an unverified or most recent snapshot.
45 3 * * * jms cd /srv/jms && /usr/bin/node dist/cli/jms.js prune \
  >> /var/log/jms/backup.log 2>&1

# Optional 15-minute snapshots for a tighter RPO. Keep only 96 of them.
*/15 * * * * jms cd /srv/jms && /usr/bin/flock -n /srv/jms/data/jms.ops.lock \
  /usr/bin/node dist/cli/jms.js backup --tag hourly --keep 96 \
  >> /var/log/jms/backup.log 2>&1

Rules for the cron entry:

  • Run as the unprivileged service user (jms), never root.
  • Use flock -n on the same lock file the app uses for restore/migrate, so jobs cannot overlap or race a restore.
  • Redirect both streams to a log file that is rotated by logrotate (daily, keep 14, compress).
  • Use an absolute working directory and absolute Node path; cron has a minimal PATH.
  • Do not put secrets on the command line; the CLI reads the same validated environment file/config as the app.
  • Set TZ=UTC so filenames and logs are unambiguous.
  • A non-zero exit is alertable. The log line is JSON so a log shipper can parse it.

ops/systemd/jms-backup.timer is the alternative:

[Timer]
OnCalendar=*-*-* 02:15:00 UTC

[Install]

17.6 Retention (GFS)

jms prune applies:

  • keep every snapshot from the last 24 hours;
  • keep the newest snapshot per day for 30 days;
  • keep the newest snapshot per ISO week for 12 weeks;
  • keep the newest snapshot per calendar month for 12 months;
  • never delete the newest verified snapshot, a pre-migrate/pre-restore snapshot younger than 7 days, or any snapshot whose manifest is missing/failed;
  • delete the .db, .sha256 and .json as a unit, and only after a dry-run count is logged.

--dry-run is the default for manual use; cron passes --apply. The retention job writes an audit row (backup.prune) with the count and names removed (names only, no contents).

17.7 Offsite copies

Local backups do not survive disk loss. Production must copy snapshots off the host:

# In BACKUP_OFFSITE_CMD, run after the local backup is verified.
restic -r s3:s3.example.com/jms backup /srv/jms/backups \
  --tag jms --host jms-prod-1

or

rclone copy /srv/jms/backups remote:jms-backups --immutable

Rules:

  • Offsite storage is encrypted at rest and in transit; restic handles both.
  • The offsite job runs only after the manifest is written.
  • Verify a random offsite snapshot monthly by restoring it to a scratch host.
  • Keep the restic/rclone credentials out of the application environment; use the service user's credential file with mode 0600.
  • The generated PDFs in storage/documents/ are regenerable and are not required for disaster recovery. They are included in an optional weekly archive if storage permits.

17.8 Restore procedure

jms restore --from <name> --force is the only supported path. It is destructive and requires confirmation.

  1. Acquire the ops lock; refuse if the app is running (detect the app lock PID) unless --offline is passed and the app is confirmed stopped.
  2. Verify the chosen snapshot: checksum, manifest, integrity_check, foreign_key_check and a smoke query. Refuse an unverified file.
  3. Write a pre-restore snapshot of the current database if it is readable.
  4. Copy the snapshot to data/.restore-<timestamp>.db, fsync, then: - stop accepting new writes (the app must already be stopped); - rename the current database to data/jms.sqlite.pre-restore-<timestamp>; - remove any stale jms.sqlite-wal and jms.sqlite-shm (they belong to the old file); - rename the restored file to data/jms.sqlite.
  5. Open the restored database, run PRAGMA integrity_check, PRAGMA foreign_key_check, PRAGMA optimize, and set PRAGMA user_version to the packaged version if the manifest matches.
  6. Revoke every session (UPDATE sessions SET revoked_at = :now WHERE revoked_at IS NULL) unless --keep-sessions is explicitly passed. This prevents an old cookie from authenticating against rolled-back data.
  7. Delete idempotency keys and rate-limit rows older than the snapshot horizon.
  8. Write an audit row backup.restore with the source name, checksum and operator.
  9. Print the restored counts and the next step: start the app, run /healthz, sign in, open one job, one invoice and the audit view.
  10. Release the lock.

The restore command never edits the snapshot in place. It works on a copy, so a failed restore leaves the original snapshot intact.

17.9 Restore drills

  • Before go-live, perform a full drill and record date, backup name, verifier, duration and result in the ops log.
  • Monthly thereafter, restore the latest offsite snapshot to a scratch environment and run the smoke checks.
  • The drill is not complete until a user can sign in, open a job, open an invoice, download a PDF and see a new audit row.
  • A failed drill is a release blocker, not a backlog item.

17.10 Monitoring

  • /healthz returns backup: { last_ok_at, age_hours, last_file, verified }.
  • 503 when age_hours > BACKUP_MAX_AGE_HOURS; the page names the last verified file.
  • The exit code of the cron command is the primary alert signal. Configure cron mail or a monitoring agent to alert on non-zero.
  • A dead-man's switch (healthchecks.io, Cronitor or a self-hosted equivalent) is pinged after a successful backup and verification; a missed ping alerts.
  • Disk space is checked before every backup and exposed in /healthz as a warning below 1 GB.
  • backups/last-success.json (written atomically) lets an external check run without the app.

17.11 Backup tests

Automated tests in tests/backup/ must prove:

  • a backup runs while a writer is active and the snapshot passes integrity_check;
  • the snapshot's counts match the live database at commit time;
  • a tampered .db fails checksum verification;
  • a truncated .db fails integrity_check and is never restorable;
  • a missing manifest makes a snapshot ineligible for pruning and restore-by-latest;
  • prune --dry-run removes nothing; --apply removes exactly the GFS set;
  • restore to a temp path succeeds, revokes sessions, and a sign-in is required;
  • restore refuses while the app lock is held;
  • a failed restore leaves the original database and snapshot untouched;
  • retention never deletes the newest verified snapshot;
  • the backup CLI exits non-zero on a failing integrity check.

The HTTP workflow suite includes a test that starts the app on a backup/restore round-trip and asserts the seed counts and a readable job.

19.2 Production

  • One Node process behind a reverse proxy (Caddy/Nginx) with HTTPS.
  • Persistent volume for data/, storage/ and backups/; backups/ mode 0700.
  • NODE_ENV=production, COOKIE_SECURE=true, a strong SESSION_SECRET, TRUST_PROXY=true, SQLITE_SYNCHRONOUS=FULL.
  • Build on deploy: npm ci --omit=dev, npm run build, npm run db:migrate (with the app stopped), then npm start under systemd.
  • Run npm run seed only on first deploy.
  • Health check: GET /healthz returns 200 {"status":"ok","db":"ok","schema":2, "backup":{"age_hours":6.2,"verified":true},"sqlite":"3.49.1"}.
  • Graceful shutdown on SIGTERM/SIGINT: stop accepting, drain in-flight requests with a 10-second cap, run PRAGMA wal_checkpoint(TRUNCATE), PRAGMA optimize, close the database, release the app lock, exit 0. A forced second signal exits 1.
  • No horizontal scaling against one database in v1. A future move to a server database would revisit the rate limiter, sessions and single-writer assumptions.
  • Log rotation: systemd/journald or logrotate; application logs are JSON lines.
